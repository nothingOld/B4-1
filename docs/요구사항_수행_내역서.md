# 요구사항 수행 내역서

## 1. 과제 개요

- **분야:** AI/SW 기초
- **구분:** Linux와 OS
- **미션:** 컴퓨터가 알아서 자기 상태를 점검하게 만들기
- **자동화 스크립트:** Bash
- **보너스 과제:** 수행하지 않음
- **목표:** Linux 서버의 기본 보안, 역할 기반 권한, 애플리케이션 실행 환경, 시스템 관제, 로그 관리 및 cron 자동화를 구성한다.

## 3. SSH 보안 설정

### 3.1 수행 내용

SSH 기본 포트를 `20022`로 변경하고 Root 계정의 원격 로그인을 차단하였다.

설정 파일은 `/etc/ssh/sshd_config.d/99-agent.conf`를 사용하였다.

```text
Port 20022
PermitRootLogin no
```

### 3.2 주요 명령어

```bash
grep -n "Include" /etc/ssh/sshd_config

sudo tee /etc/ssh/sshd_config.d/99-agent.conf > /dev/null <<'EOF'
Port 20022
PermitRootLogin no
EOF

sudo sshd -t
sudo systemctl restart ssh

sudo sshd -T | grep -E '^(port|permitrootlogin)'
sudo ss -lntp | grep 20022
```

### 3.3 검증 결과

- SSH 적용 포트: `20022`
- `PermitRootLogin`: `no`
- `sshd`가 `0.0.0.0:20022`, `[::]:20022`에서 LISTEN 상태임을 확인하였다.

![SSH 설정 확인](../images/ssh/01_ssh_security_config.png)

## 4. 방화벽 설정

### 4.1 수행 내용

Ubuntu의 UFW를 사용하여 기본 인바운드 정책을 차단하고, 미션에 필요한 두 개의 TCP 포트만 허용하였다.

| 구분 | 설정 |
|---|---|
| 기본 Inbound | `deny` |
| 기본 Outbound | `allow` |
| SSH | `20022/tcp ALLOW IN` |
| Application | `15034/tcp ALLOW IN` |
| UFW 상태 | `active` |

### 4.2 주요 명령어

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing

sudo ufw allow 20022/tcp
sudo ufw allow 15034/tcp

sudo ufw --force enable
sudo ufw status verbose
```

### 4.3 검증 결과

`sudo ufw status verbose` 결과에서 UFW 활성 상태, 기본 인바운드 `deny`, TCP `20022`, `15034` 허용을 확인하였다.

![UFW 상태](../images/firewall/01_ufw_status.png)

sudo mkdir -p /var/log/agent-app

sudo setfacl -m g:agent-common:--x /home/agent-admin

sudo chown agent-admin:agent-common /home/agent-admin/agent-app
sudo chmod 2770 /home/agent-admin/agent-app

sudo chown agent-admin:agent-common /home/agent-admin/agent-app/upload_files
sudo chmod 2770 /home/agent-admin/agent-app/upload_files
sudo setfacl -m g:agent-common:rwx /home/agent-admin/agent-app/upload_files
sudo setfacl -d -m g:agent-common:rwx /home/agent-admin/agent-app/upload_files

sudo chown agent-admin:agent-core /home/agent-admin/agent-app/api_keys
sudo chmod 2770 /home/agent-admin/agent-app/api_keys
sudo setfacl -m g:agent-core:rwx /home/agent-admin/agent-app/api_keys
sudo setfacl -d -m g:agent-core:rwx /home/agent-admin/agent-app/api_keys

sudo chown agent-admin:agent-core /home/agent-admin/agent-app/bin
sudo chmod 2770 /home/agent-admin/agent-app/bin

sudo chown agent-admin:agent-core /var/log/agent-app
sudo chmod 2770 /var/log/agent-app
sudo setfacl -m g:agent-core:rwx /var/log/agent-app
sudo setfacl -d -m g:agent-core:rwx /var/log/agent-app

## 7. 애플리케이션 실행 환경

### 7.1 애플리케이션 배치

제공받은 `agent-app-linux-x86` 파일을 다음 경로에 배치하였다.

```text
/home/agent-admin/agent-app/agent-app-linux-x86
```

애플리케이션은 Root가 아닌 `agent-admin` 계정으로 실행하였다.

### 7.2 환경 변수

실제 실행 환경에는 다음 변수를 설정하였다.

```text
AGENT_HOME=/home/agent-admin/agent-app
AGENT_PORT=15034
AGENT_UPLOAD_DIR=/home/agent-admin/agent-app/upload_files
AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys
AGENT_LOG_DIR=/var/log/agent-app
```

환경 변수는 `/home/agent-admin/agent-app/agent-env.sh`에서 관리하고 `agent-admin` 로그인 환경에서 로드하도록 구성하였다.

### 7.3 키 파일

과제 명세에서는 다음과 같이 안내되어 있었다.

```text
AGENT_KEY_PATH=$AGENT_HOME/api_keys/t_secret.key
키 파일: $AGENT_HOME/api_keys/t_secret.key
```

그러나 실제 제공 바이너리의 Boot Sequence 검증 결과 다음 조건을 요구하였다.

```text
AGENT_KEY_PATH=/home/agent-admin/agent-app/api_keys
Expected key file=/home/agent-admin/agent-app/api_keys/secret.key
```

따라서 과제 명세용 `t_secret.key`를 유지하면서, 제공 바이너리의 실제 검증 조건을 만족하기 위해 동일한 테스트 키 문자열을 가진 `secret.key`도 추가 구성하였다.

테스트 키 문자열:

```text
agent_api_key_test
```

### 7.4 실행 명령어

```bash
sudo -iu agent-admin

env | grep '^AGENT_'

/home/agent-admin/agent-app/agent-app-linux-x86
```

### 7.5 실행 결과

Boot Sequence의 5단계가 모두 `[OK]`로 통과하고 최종적으로 `Agent READY`가 출력되는 것을 확인하였다.

## 8. `monitor.sh` 구현

### 8.1 파일 정보

| 항목 | 값 |
|---|---|
| Repository 소스 | `bin/monitor.sh` |
| 운영 경로 | `/home/agent-admin/agent-app/bin/monitor.sh` |
| 소유자 | `agent-dev` |
| 그룹 | `agent-core` |
| 권한 | `750 (rwxr-x---)` |
| cron 실행 계정 | `agent-admin` |

### 8.2 구현 기능

`monitor.sh`는 다음 순서로 시스템 상태를 점검한다.

1. `agent-app-linux-x86` 프로세스 확인
   - 비정상 시 `[FAIL]` 출력 후 `exit 1`
2. TCP `15034` LISTEN 상태 확인
   - 비정상 시 `[FAIL]` 출력 후 `exit 1`
3. UFW 활성 설정 확인
   - 비활성 상태면 `[WARNING]` 출력
   - 스크립트는 종료하지 않음
4. CPU 사용률 수집
5. 메모리 사용률 수집
6. Root 파티션 디스크 사용률 수집
7. 임계값 초과 여부 확인
8. 결과를 `/var/log/agent-app/monitor.log`에 기록

### 8.3 임계값

```text
CPU > 20%       -> [WARNING]
MEM > 10%       -> [WARNING]
DISK_USED > 80% -> [WARNING]
```

### 8.4 로그 형식

```text
[YYYY-MM-DD HH:MM:SS] PID:... CPU:..% MEM:..% DISK_USED:..%
```

## 9. 로그 용량 관리

### 9.1 정책

`logrotate`를 사용하여 다음 정책을 구성하였다.

```text
대상: /var/log/agent-app/monitor.log
회전 기준: 10MB
보관 개수: 10개
압축: 적용
새 로그 권한: 0660 agent-admin:agent-core
```

### 9.2 설정

`/etc/logrotate.d/agent-app`

```text
/var/log/agent-app/monitor.log {
    size 10M
    rotate 10
    missingok
    notifempty
    compress
    delaycompress
    create 0660 agent-admin agent-core
    su agent-admin agent-core
}
```

### 9.3 검증

디버그 모드로 설정을 검증한 후 강제 회전을 수행하였다.

```bash
sudo logrotate -d /etc/logrotate.d/agent-app
sudo logrotate -f /etc/logrotate.d/agent-app
```

설정에서 `size 10M`, `rotate 10`을 확인하였다.

![logrotate 설정](../images/automation/01_logrotate_config.png)

강제 회전 후 `monitor.log`와 `monitor.log.1`이 생성됨을 확인하였다.

## 12. 대상 서비스 변경 시 점검 항목

현재 `monitor.sh`는 `agent-app-linux-x86`과 TCP `15034`를 기준으로 관제하도록 구현하였다.  
다른 웹서버 또는 애플리케이션으로 전환할 경우에는 단순히 프로세스명만 변경하는 것이 아니라 다음 항목을 함께 확인해야 한다.

| 확인 항목 | 현재 설정 | 변경 예시 |
|---|---|---|
| 프로세스명 | `agent-app-linux-x86` | `nginx`, `java`, `gunicorn` 등 |
| 실행 파일/프로세스 식별 기준 | `/home/agent-admin/agent-app/agent-app-linux-x86` | 대상 서비스 실행 경로 |
| 서비스 포트 | `15034` | `80`, `443`, `8080` 등 |
| 방화벽 허용 포트 | `15034/tcp` | 변경된 서비스 포트 |
| 로그 경로 | `/var/log/agent-app` | 대상 서비스 로그 경로 |
| CPU 임계값 | `20%` | 서비스 특성에 맞게 조정 |
| MEM 임계값 | `10%` | 서비스 특성에 맞게 조정 |
| DISK 임계값 | `80%` | 운영 정책에 맞게 조정 |

따라서 새로운 서비스를 관제할 때는 **프로세스 식별 조건, LISTEN 포트, 방화벽 규칙, 로그 위치, 자원 임계값을 함께 검토해야 한다.**

## 13. 프로세스는 실행 중이나 포트가 열리지 않는 경우의 점검 절차

프로세스가 실행 중이라는 사실만으로 애플리케이션이 정상적으로 서비스를 제공하고 있다고 판단할 수 없다.  
프로세스는 살아 있지만 포트 바인딩에 실패하거나 초기화 과정에서 문제가 발생할 수 있기 때문이다.

다음 순서로 원인을 점검한다.

### 13.1 프로세스 존재 여부 확인

```bash
pgrep -a -f agent-app-linux-x86
```

PID가 존재하는지 확인한다.

### 13.2 서비스 포트 LISTEN 상태 확인

```bash
ss -lntp | grep 15034
```

프로세스는 존재하지만 `15034`가 LISTEN 상태가 아니라면 애플리케이션이 정상적으로 포트를 바인딩하지 못한 상태일 수 있다.

### 13.3 동일 포트 선점 여부 확인

```bash
ss -lntp | grep ':15034'
```

다른 프로세스가 동일 포트를 이미 사용하고 있는지 확인한다.

### 13.4 애플리케이션 실행 로그 확인

애플리케이션 시작 과정에서 다음과 같은 원인을 확인한다.

- `Address already in use`
- `Permission denied`
- 환경변수 오류
- 초기화 실패
- 바인딩 주소 오류

### 13.5 방화벽 상태 확인

```bash
sudo ufw status
```

애플리케이션이 LISTEN 중인데 외부에서 접근할 수 없다면 방화벽에서 해당 포트가 허용되어 있는지 확인한다.

점검 순서는 다음과 같다.

```text
프로세스 확인
→ LISTEN 포트 확인
→ 포트 충돌 확인
→ 애플리케이션 로그 확인
→ 방화벽 확인
```

`monitor.sh`에서 프로세스 검사와 포트 검사를 별도로 수행하는 이유는 **“프로세스가 살아 있음”과 “서비스가 실제 요청을 받을 수 있음”이 서로 다른 상태이기 때문**이다.
